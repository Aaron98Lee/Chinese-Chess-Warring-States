# 11 — Quality Standards and Acceptance Criteria

| | |
|---|---|
| Document status | **Draft v0.1, submitted for approval** |
| Date | 2026-11-20 |
| Principle | A feature is done only when it meets its functional requirements, passes its tests, integrates correctly, performs within budget and is documented. **No test is reported as passed unless it has been executed and its evidence recorded.** |

Each criterion has an ID, a measurable threshold, a measurement method and the milestone from which it is enforced.

---

## 1. Definition of Done (every work item)

- [ ] Meets its written requirement and acceptance criteria
- [ ] Automated tests added or updated, and passing in CI
- [ ] Integrated on the target branch without breaking other tests
- [ ] Within performance and asset budgets (where applicable)
- [ ] Documentation updated (API docs, ADRs, register entries, user-facing text)
- [ ] Reviewed (code review; art review; historian review for history-bearing assets)
- [ ] No new placeholder content in release-bound paths
- [ ] Licences recorded for any new asset or dependency

## 7. Testing process standards

- **Test register:** every executed test run is recorded with date, build or commit, environment, result and evidence (CI link, log, screenshot, report). The register is the only valid basis for any "passed" statement.
- **CI gates:** core library tests on every push; Unity tests and build on every pull request (once Unity CI is configured); nightly AI self-play and performance captures.
- **Coverage:** `Xiangqi.Core` ≥ 95% line and ≥ 90% branch coverage; `Xiangqi.Session` ≥ 90% line. Coverage is a floor, not a goal; the rule-case corpus (QG-02) is the primary correctness measure.
- **Regression:** every fixed bug gets a regression test (rules bugs: a FEN-based case in the corpus).
- **Integration:** a Unity play-mode test asserts state and visual agreement after randomised event sequences, including skips, undos and speed changes (VS-T02).
